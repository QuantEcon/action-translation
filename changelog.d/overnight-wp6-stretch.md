### Fixed

- **Rebase mode stops with a comment that names the lecture, instead of a missing-title error, when a PR merged since added a lecture this PR's source change adds too** (#467). Two translation PRs can add the same lecture: the sync of a source PR and a `\translate-resync` of it, or the syncs of two source PRs that both add it. Once one merged, rebase mode rebuilt the other as an update of `main`'s copy, with no earlier English to diff against, and failed with a missing-title error from the section parser that named neither PR (before any model call, with the branch as it was). When `main` has a lecture, rebase now also reads it at the PR's baseline; when the baseline lacks it and the English before the PR's source commit does too, it reads the PR's branch, and a branch that has the lecture stops the rebase of that PR before anything is translated or pushed. The failure comment names the lecture, asks a person to decide which copy wins, and says a later rebase of the PR stops there again until the PR merges or closes; it offers no `translate forward` or resync for it, which would make a third translation. A lecture `main` got since the PR opened that the PR's source change only edits, as when a second source PR edits a lecture before the edition merges the first one's sync, is still rebased as an update of `main`'s copy, with one model call per edited section. A failed read of the baseline, the source parent or the branch, other than a 404, fails the rebase of that PR where it decides the outcome. An ordinary update makes the same reads as before (the rebase cache reuses the new baseline read); a lecture the PR never delivered that `main` has, and a renamed lecture `main` still has under its old path, each cost one read more.
- **A lecture's state file keeps the keys the engine does not own** (#290). Every writer rebuilt `.translate/state/<file>.yml` from its six fields, so any other key, such as the editor sign-off block (`reviewed:`) an edition-side workflow is to record, was erased by the next sync, `init`, `forward` (on disk and with `--github`), `status --write-state` or rebase. Each writer now reads the existing file and keeps every top-level key it does not own after the engine's keys, which keep their order and formatting: a state file with no other key is written byte for byte as before, so sync PRs carry no new state-file churn. A kept key is carried as the text it was, with the lines under it and the comment lines above it (line endings made LF), so `target-sha: 0123456` keeps its leading zero and a comment beside a sign-off stays; comments among the engine's own keys are lost. Where the text cannot be carried as written (a byte-order mark, a tab, several YAML documents, a flow mapping or complex key at the top, a kept key aliasing an anchor in an engine key, or a value that would not load back the same), the kept keys are written from their values instead, with a warning that quoting, comments and number formatting may have changed. A renamed lecture's state file moves with its other keys unless the new path already has one; a removed lecture's state file is still deleted. An existing state file that is not a YAML mapping, one that repeats a key included, is overwritten with a warning naming it, and the sync PR's body lists it under "State Files Overwritten" (`status --write-state` still refuses one without `--force`); an empty or comment-only one is overwritten with a warning that it held no keys. The sync Action and rebase mode reuse the state-file reads they already made, so they make no extra read; a lecture whose own state file the edition answers with anything but a 404 is now held back instead of being written over: sync lists it in the failure issue, which advises a `\translate-resync` once the file reads again (under the usual condition), and rebase fails that PR's rebase with the branch untouched and a comment that advises re-running the workflow. Rebase mode rebuilds a lecture's state file from the copy on the edition's default branch at the commit it rebases onto: a key added there since the PR opened is kept, and a key that exists only in the state file on the PR's branch is not, except for a lecture the PR adds, whose state file is carried from the branch unchanged. Before release, exercise this on the `test-translation-sync` lanes with a state file carrying an extra key, as #290 asks; it was not run here, since the harness makes billed model calls.
- **A review finding that quotes another lecture of the PR is filed under that lecture** (#223). The reviewer sometimes names one file while its description quotes another file of the same PR (lecture-python.zh-cn#208: an accuracy finding on `kesten_processes.md`'s Gibrat section quoting `olg_adaptive_money.md`), so an editor sent there found nothing to act on. On a PR that reviews more than one file, review mode now checks the text each reviewer finding quotes in its description (in backticks or quotation marks, 6 characters or more; never the suggestion, which proposes text) against every reviewed file's English and translation, before and after the PR. The comparison folds whitespace, compatibility forms (full-width against half-width), emphasis markers, backticks, MyST role prefixes, apostrophes and case, and compares a quote with CJK characters with all whitespace removed. The finding is moved, with its location cleared, only when the named file has both texts and holds none of the quotes (also searched with all whitespace removed), every quote found is in one and the same other file, there are two such quotes or one of 20 characters or more, and no quote is found nowhere except one beside two found (the reviewer's own proposed wording, as in the #208 finding). Otherwise, as when a quote is common to several lectures, is a glossary term or a short phrase, or is the named file's own text in a form the comparison misses, it is left as the reviewer wrote it. A single quote of 20 characters or more that only another file holds can still move a finding that merely cites that file. Severity, category and text never change, no finding is dropped, and routing is unchanged; each move is logged in the run. The verdict schema is unchanged, but verdict records may now attribute such a finding to a different file than before, which matters for per-file shadow data across this release. A finding left where it is keeps its file and location as before.
