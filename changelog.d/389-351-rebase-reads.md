### Fixed

- **Rebase no longer brings back a lecture a merged PR deleted, or re-translates a lecture the PR adds** (#389, #351). Rebase mode read each lecture of a sibling PR on `main` alone, and took any failed read for a lecture new to the edition, which it translated from scratch. When a merged PR had deleted the lecture, the rebased PR re-added it, freshly translated in place of the PR's reviewed update, under a "translation content is preserved" comment (#389). A lecture the PR itself adds could never use the rebase cache, which needs the file at the PR's baseline, so every rebase replaced its reviewed translation with a new one (#351: lecture-intro.zh-cn#309's `wealth_tax.md`, where only the parity check stopped it). When `main` answers 404, rebase now also reads the lecture at the PR's baseline, `main` as it was when the PR opened, and then on the PR's branch. It decides from what it finds (`rebase-plan.ts`):
  - **At the baseline but not on `main`:** a PR merged since deleted the lecture. While the PR's branch still has it, the rebase fails before the branch moves, and its comment says the rebase does not bring a deleted lecture back. If the deletion stands, the lecture and its state file come off the PR's branch, and later rebases leave it out. If the lecture should stay, it is restored on `main` first. The comment no longer offers `translate forward` for that lecture, and names a rename by both its paths.
  - **Only on the branch:** the PR adds the lecture. It and its state file are carried unchanged into the rebased commit, with no model call.
  - **Nowhere:** a lecture the PR never delivered, such as a new lecture whose translation failed. It is translated as new, as before, so a rebase can deliver a lecture that the sync's failure issue still lists, under the usual "rebased" comment.

  A rename is looked up by its old path on `main` and at the baseline. When `main` lacks the old path but already has the new one, as after another PR made the same move, the rename is rebuilt as an update of the new path. A read that fails with any status but 404, on any of the three, fails the rebase with the branch untouched, where it used to translate the lecture as new. So does a 404 on `main` for a PR opened before the rebase cache, which records no baseline to tell the cases apart.
